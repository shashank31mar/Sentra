## 1. Shared conventions

- **Flags (mirror ML-classifier, best-practices §14):** `CEDAR_ENABLED` (run the validator) + `CEDAR_SHADOW_MODE` (run + log, do **not** influence the verdict). Off by default. `CEDAR_SCHEMA_VERSION`.
- **Storage model (decided — resolves the C6 "where do the fields live" gap):** the **structured `AgentPolicyDocument` is the stored SOURCE OF TRUTH** at its **existing key/extension** (S3 `policies/agents/{id}/v{version}.yaml` — **no rename**), and the **`.cedar` text is a GENERATED CO-ARTIFACT** at the **same key, extension swapped** (`…/v{version}.cedar`) — **not a replacement**. **Addressing (no new key field):** metadata `s3_key` keeps pointing at the structured source; the `.cedar` key is **derived by convention** (swap the extension). `content_hash` hashes the **structured source**; the compiled-Cedar cache key is **`schema_version` + `content_hash` + `generator_version`** (the `.cedar` is a function of all three — a generator fix changes `.cedar` from the same source, so `generator_version` is required, see CT06/CT08). Both objects exist; `policy_format=cedar` only flips *which one drives authz* (CedarPolicyEngine reads `.cedar`), it does **not** delete the structured source. This is what makes CT12's "structured-is-the-only-editor, Cedar-is-read-only-generated, no round-trip" actually work — the structured doc is persisted, re-editable, and re-generates the `.cedar`.
  - **The loader sources every non-Cedar field from the structured object, never from the `.cedar` text:** `allowed_callers` (translated to Cedar *nowhere* — C6/CT08), `cross_cloud_dependencies` (the **full** list — target_agent/target_tool/max_age_seconds — which the Cedar `Tool.requires_precondition` boolean does **not** preserve), `max_calls_per_minute`, `platform`, `cloud_region`. `CedarPolicyEngine` reads the `.cedar`; everyone else reads the structured dict.
  - Shared schema at `schema/agent-policy-v{n}.cedarschema`; metadata row gains `policy_format` (`yaml`|`cedar`). No new table, no key/GSI change.
- **Signal contract (locked):** `CedarPolicyEngine` emits `Source.SENTRA_POLICY` with the existing DENY `violation_type`s. Combiner/audit untouched.
- **Fail-secure:** evaluator error / no policy / parse failure → DENY (never fail-open).
- **Boundary:** Cedar = authorization decision only; pipeline gathers context + keeps trust/sigma/ML/rate (feature §5).

**Key model decision (consistent with feature §6.1 — record for CT09/CT10):** the Cedar **authorization rules are universal** (the single `baseline-v1.cedar`, derived from `policy_engine`'s real hardcoded checks). **All per-agent variance is entity-borne** — `allowed_tools`/`allowed_agents`/`max_refund_amount`(cents, $5,000 default)/`requires_precondition` are synthesized into the Cedar entity store per request (CT05b), NOT baked into the `.cedar` text. So each migrated policy's `.cedar` **is** the baseline rule set; the structured `.yaml` stays the human-facing per-agent config (shown via CT06b). The translator therefore validates expressibility + stamps metadata rather than emitting bespoke per-agent rules; the inert `policies[].rule` strings are inventoried and dropped (C2). Cross-cloud/rate rules are present in the baseline but **inert unless the policy declares `cross_cloud_dependencies`** (then CT05b marks the tool, and the divergence vs `policy_engine` is the cedar-intentional superset CT09 triages). The one intentional fail-secure improvement over `policy_engine`: a missing/non-coercible refund `amount` is **denied-on-missing**, not defaulted to `$0` + allowed.

**Code-review corrections (2026-06-13, pre-cutover):**
- **Cross-cloud is NOT enforced by Cedar — explicitly deferred.** The earlier baseline `forbid_cross_cloud_precondition` + `Tool.requires_precondition` + `CrossCloudCall` action were **dead code**: the synthesizer keyed off a `cross_cloud_dependencies[].tool` field that does NOT exist (real shape is `required_before`/`target_agent`/`target_tool`/`max_age_seconds`), and `preconditions_met` was never threaded into the engine. All of it was **removed**; cross-cloud sequence enforcement stays in `context_validator` (as in legacy — parity preserved). Test fixtures that fabricated `{"tool": …}` were corrected to the real shape and now assert Cedar does *not* enforce cross-cloud. Re-enabling it later means threading context_validator's computed `preconditions_met` into `CedarContext` + a guarded rule.
- **Allow-list FIRST (matches legacy check order).** Dangerous-tool forbids are resource-scoped, not allow-list-gated, so a `process_refund`/`verify_identity` **not in `allowed_tools`** with an over-cap amount / `fraud_risk=high` would have reported `POLICY_VIOLATION`/−10 (or fraud −15) instead of legacy's `UNAUTHORIZED_TOOL`/−15 — a penalty drift at cutover. `_map_use_tool_deny` now checks allow-list membership first; parity corpus extended with these cases.
- **Deterministic priority collapse.** Forbid→reason mapping uses an explicit priority tuple, not alphabetical `@id` order.
- **Schema uses the EMPTY namespace** (`""`) with unqualified `Agent`/`Tool`/`Action::"UseTool"` — NOT the `Sentra::`-namespaced form CT02's note sketched. Internally consistent; the CT02 prose is the stale one.

**Resolved `cedarpy` 4.8.4 API (for CT09+):** `is_authorized(request_dict, policies_str, entities_str)`; `AuthzResult.decision` ∈ {`Decision.Allow`,`Decision.Deny`}; determining rules via `diagnostics.reasons` (positional ids) resolved through `diagnostics.id_annotations_by_reason` → the `@id("…")` names; malformed policy/entities come back as `Decision.Deny` + `diagnostics.errors` (NOT raised) → mapped to `POLICY_ERROR`; `validate_policies(policies, schema)` (note arg order).
